How TraitTrack is organized

TraitTrack is organized around the project, rather than around an individual device. One project has a single owner and one or more collaborators, allowing everyone to contribute to the same shared experiment.

👤

Project owner

The owner has the complete synchronized project view and uses the dashboard to monitor collection, collaborator activity, imagery, metadata, and project-level statistics.

👥

Collaborators

Collaborators use their individual iOS devices to record observations and attach photographs or supported media to the appropriate experimental entries.

🌱

Plots and entries

A project contains experimental entries or plots. Observations are associated with the appropriate plot and trait.

🧬

Traits

Trait definitions describe what is being measured and which format is used to record the observation.

Key idea: Multiple devices contribute to one continuously reconciled project instead of creating separate datasets that must be merged after the field season.

What is stored with an observation?

Every observation is a first-class project record. TraitTrack retains the information needed to identify what was measured, where it was measured, who recorded it, and how the record has changed.

Plot or entry identifier

Identifies the experimental unit associated with the observation.

Trait identifier and format

Identifies the trait and the format used to record its value.

Recorded value

Stores the actual field observation.

Observer

Records the collaborator who contributed the observation.

Collection and modification times

Preserves when the observation was collected and subsequently modified.

Synchronization status

Tracks the record's synchronization state as it moves between device and shared backend.

Photograph or media reference

Connects supporting imagery or other media to the experimental record.

Notes and project metadata

Stores user-entered notes and additional metadata defined for the project.

Text, numeric, percent, angle, categorical/qualitative, Boolean, date, counter, and scale.

Disease rating, stopwatch, and location/GNSS formats.

Media

Photo, audio, and video formats allow observations to include supporting evidence.

Identification

Barcode-based collection is supported for identifying field material or experimental units.

Hardware-assisted workflows

Fallback collection

Understanding synchronization

TraitTrack synchronization is near-real-time, not instantaneous. While a project is active, the client initiates a reconciliation cycle at a nominal 30-second interval, subject to network availability and backend response time.

Push local changes

The device sends new or modified observations, corrections, photographs, notes, metadata, presence information, and project-progress information to the backend.

Backend reconciliation

The shared backend reconciles concurrent changes and maintains the common project state.

Pull merged state

Clients retrieve the merged project state during the synchronization cycle.

Refresh the owner dashboard

The dashboard updates its project-level metrics using the reconciled information.

Remember: A successful observation upload does not necessarily mean that a large photograph has finished transferring. TraitTrack distinguishes observation synchronization from pending or completed media uploads.

Corrections and conflicting edits

Multi-user collection means more than one device can contribute to the same project. TraitTrack therefore uses unique record identifiers and explicit update rules to prevent duplicate records when the same local change is transmitted across multiple synchronization cycles.

Why provenance matters

Corrections do not silently erase the distinction between an original field observation and a later revision. The synchronized record retains its submitting user, plot and trait identifiers, collection and modification times, and synchronization information.

For project owners: If two users modify the same observation, use the application's conflict-detection and resolution workflow rather than attempting to reconcile competing values manually in separate files.

TraitTrack storage backends

The manuscript describes two supported backend approaches. The application can be used with familiar shared storage or with a dedicated collaboration server.

Google Drive

Suitable for groups that want to use a familiar shared-storage environment. Google Drive is treated as a project/provider identifier rather than as a live concurrent document-mutation target.

FastAPI + PostgreSQL

A dedicated collaboration backend provides shared persistence and conflict-safe reconciliation through REST endpoints.

Amazon S3 media storage

The server-based architecture can optionally use Amazon S3 for media attachments.

Local or hosted deployment

The backend can be run locally for same-network device testing or deployed as a hosted service.

Using TraitTrack for in-season quality control

One of TraitTrack's main advantages is that project oversight happens while collection is still underway.

Watch for incomplete areas

A trait or section with unusually few observations can be identified before the team leaves the field.

Check collaborator synchronization

A device that has not recently synchronized may indicate that its observations have not reached the shared project state.

Review suspicious values

Clusters of values that warrant review can be investigated while the relevant plots are still accessible.

Use imagery for verification

Provenance-linked photographs can help determine whether an unusual observation reflects the phenotype or a scoring problem.

Return to the field when needed

Because issues are visible during collection, missing or questionable observations can potentially be re-measured before the field season ends.

Important limitations

The current manuscript identifies several areas that users and administrators should understand when interpreting TraitTrack behavior.

  • The 30-second synchronization cycle is near-real-time rather than instantaneous.
  • Actual synchronization latency depends on network quality, backend response time, media size, collaborator count, and the amount of data exchanged.
  • Field environments may have intermittent connectivity, so unsynchronized records can be queued locally and transferred when connectivity returns.
  • Large media files may require more time and bandwidth than scalar observations.
  • Concurrent edits to the same observation can create conflicts that require conflict detection and resolution.
  • Broader evaluation of authentication, collaborator permissions, encryption, backup, and recovery from interrupted synchronization was still ongoing in the manuscript.

Recommended project-owner workflow

For project owners, TraitTrack is designed around continuous oversight rather than waiting until the end of collection.

Prepare the project

Configure the experiment, entries, traits, collaborators, and any required metadata.

Start collection

Have collaborators collect plot- and trait-level observations, photographs, and notes.

Monitor synchronization

Use recent synchronization information and collaborator activity to determine whether contributions are reaching the shared project.

Monitor completion

Look for incomplete locations, plots, traits, or collaborator assignments.

Perform in-season QC

Review questionable observations and provenance-linked imagery while field access remains available.

Review and export

After collection is complete, review the final project state and export the data and associated media needed for downstream analysis.

Troubleshooting

My data is not synchronizing

Check connectivity, pending uploads, and the synchronization status. Try again when a stable connection is available.

I cannot see a project

Confirm that you have been added as a collaborator and that you are signed into the correct account.

An observation is missing

Check the local device and synchronization status before assuming that the observation was lost.

The app is behaving unexpectedly

Record the project, device, application version, and steps that produced the problem when reporting an issue.
